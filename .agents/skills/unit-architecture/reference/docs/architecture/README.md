# Архитектурная модель

Unit Architecture строится вокруг ответственности и её ближайшего владельца.

## Владение

Ответственность — связный результат или возможность приложения, изменяющиеся по одной причине. Она может быть:

- проекционной: layout, screen, Header, ProductCard;
- предметной: Products, Publications, Authentication;
- инфраструктурной: HTTP transport, Query Client, Storage;
- универсально-визуальной: Button, Select, Modal;
- фундаментальной: чистое преобразование или общий тип без продуктового смысла.

Каждая самостоятельная ответственность получает ровно один юнит-владелец. Вид файлов внутри юнита не определяет его роль: наличие JSX, Provider, hook или adapter не меняет ответственность и слой.

## Юнит

Юнит — папка-владелец одной ответственности, имеющая хотя бы один непустой публичный фасет. Юнит определяет:

- публичный контракт;
- зависимости;
- внутреннюю реализацию;
- состояние и область жизни ресурсов, если они нужны;
- вложенные ответственности.

Юнит может содержать любые файлы, любые выбранные проектом сегменты и вложенные юниты. Архитектура не задаёт его внутренний шаблон.

## Колокация

Код размещается у ближайшего владельца, ради ответственности которого он существует. Код не поднимается в общую область заранее. Расширение числа потребителей меняет место колокации, а появление новой ответственности меняет граф юнитов.

## Слои

Слой определяет архитектурную роль юнита и допустимые направления межслойных зависимостей. Слой не владеет кодом и не задаёт внутреннее устройство юнита.

Unit Architecture использует роли `app`, `compositions`, `domains`, `infra`, `ui` и `shared`. Пустые слои не создаются.

## Публичная граница

У юнита один логический публичный API, физически представленный одним или несколькими фасетами. Минимум один фасет обязателен и не может быть пустым.

В SPA обычно достаточно `index`. При разделении сред публичный API может быть разложен на специализированные фасеты. Имена таких фасетов определяет проект; в документации используются примеры `client`, `browser` и `server`.

## Рекурсивность

Юнит может содержать вложенные юниты. Вложенный юнит подчиняется тем же правилам, что и корневой:

- владеет одной ответственностью;
- имеет фасет;
- скрывает реализацию;
- владеет зависимостями;
- может содержать следующие вложенные юниты.

Фасет вложенного юнита доступен только его непосредственному родителю. Вложенный юнит не импортирует родителя или предков. Родитель связывает детей и при необходимости включает их возможности в собственный API.

## Порядок проектирования

1. Сформулировать ответственность без названий файлов и библиотек.
2. Найти ближайшего существующего владельца.
3. Если ответственность самостоятельна, определить новый юнит и его родителя.
4. Выбрать слой по смыслу ответственности.
5. Определить потребителей и минимальный публичный API.
6. Выбрать фасеты по средам выполнения.
7. Проверить направления зависимостей и отсутствие циклов.
8. Только после этого выбрать внутренние файлы, сегменты и framework-паттерны.

## Критерий границы

Папка становится юнитом не из-за размера или имени. Необходимы одновременно:

- отдельно формулируемая ответственность;
- собственный контракт для родителя или другого разрешённого потребителя;
- возможность скрыть внутреннее устройство;
- хотя бы один непустой фасет;
- самостоятельная граница зависимостей.

Наличие `index.ts` является необходимым структурным сигналом только тогда, когда проект объявил его фасетом. Сам файл `index.ts` без ответственности и реального API не доказывает наличие юнита.
