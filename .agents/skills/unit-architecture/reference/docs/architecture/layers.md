# Слои

Слой описывает роль ответственности и ограничивает допустимые направления зависимостей. Он не задаёт внутреннюю структуру юнита и не заменяет владельца.

## Выбор слоя

Слой выбирается по ответу на вопрос:

> Какую ответственность обеспечивает юнит для приложения?

Тип файлов не является критерием. JSX может находиться в `app`, `compositions`, `domains`, `infra` и `ui`; Provider может принадлежать предметной, инфраструктурной или проекционной ответственности.

## app

`app` запускает приложение и связывает готовые публичные API с framework runtime.

Обычно слой владеет:

- точками входа;
- маршрутами и route-level сборкой;
- подключением глобального дерева Providers;
- глобальными Error Boundaries;
- application bootstrap;
- app-wide политиками запуска.

`app` не реализует предметные сценарии, инфраструктурные клиенты или повторно используемые UI-проекции.

Технические entry-файлы framework могут находиться непосредственно в слое и не обязаны становиться юнитами, если framework определяет их форму и они не образуют самостоятельную ответственность.

## compositions

`compositions` владеет продуктовыми UI-проекциями, собирающими готовые возможности в пользовательский интерфейс.

Примеры ответственностей:

- layouts;
- screens;
- widgets;
- другие продуктовые проекции, определённые проектом.

Композиция определяет размещение, порядок, визуальную координацию и передачу данных между подключаемыми API. Она не присваивает себе предметные правила и техническую интеграцию только потому, что вызывает их из UI.

Названия групп внутри слоя определяет проект. В примерах этой документации используются `layouts`, `screens` и `widgets`: layouts задают устойчивые каркасы, screens представляют завершённые экранные проекции, а widgets — самостоятельные крупные проекции, подключаемые в layouts и screens. Это демонстрационная таксономия, а не обязательная структура Unit Architecture.

## domains

`domains` владеет предметными возможностями приложения.

Доменный юнит определяет:

- предметный контракт;
- модели, правила и исходы;
- продуктовые данные и состояние;
- адаптацию внешних источников к предметному смыслу;
- доменный UI;
- жизненный цикл предметных ресурсов.

Один домен может использовать публичный API другого домена, если связь направлена и не создаёт цикл.

## infra

`infra` владеет техническими возможностями без предметного смысла.

Примеры:

- HTTP transport;
- storage;
- telemetry transport;
- Query Client;
- feature flag transport;
- browser API adapters;
- SDK внешней платформы до адаптации к предметной модели.

Инфраструктура сообщает технические результаты и ошибки, но не называет их продуктовыми исходами.

## ui

`ui` владеет универсальными визуальными ответственностями, не зависящими от предметной модели приложения.

Примеры:

- Button;
- Select;
- Modal;
- typography;
- theme;
- универсальные interaction primitives.

Универсальность означает отсутствие продуктового смысла, а не максимальную настраиваемость. ProductCard не становится `ui` из-за props-based API.

## shared

`shared` содержит детерминированный фундамент без продуктовой, проекционной, технической интеграционной или визуальной ответственности.

Примеры:

- чистые преобразования;
- базовые типы;
- compile-time helpers;
- небольшие неизменяемые значения;
- общие детерминированные алгоритмы.

Код `shared` не взаимодействует с сетью, browser runtime, storage, framework lifecycle или продуктовым состоянием.

Небольшие leaf-файлы могут находиться непосредственно в `shared`, когда у них нет самостоятельной ответственности и публичной границы. Связный набор с собственным контрактом оформляется юнитом.

## Матрица выбора

| Вопрос | Слой |
|---|---|
| Запускает или маршрутизирует приложение? | `app` |
| Представляет готовые возможности в продуктовом UI? | `compositions` |
| Определяет предметный смысл и исходы? | `domains` |
| Даёт техническую возможность без предметного смысла? | `infra` |
| Даёт универсальную визуальную возможность? | `ui` |
| Является чистым детерминированным фундаментом? | `shared` |

Если для ответственности подходят несколько строк, формулировка слишком описывает механизм и должна быть уточнена через результат для потребителя.
