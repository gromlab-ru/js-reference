# Пробелы документации React Reference

Этот файл временно собирает нестыковки между документацией skill и рабочим `demo-app`, а также решения, для которых в
skill пока нет точной инструкции. Файл не является источником правил. Каждый пункт нужно проверить и перенести в основной
документ отдельной задачей, после чего удалить из этого списка.

## GAP-001: Форматирование импортов

**Состояние:** открыт.

Styleguide определяет публичные пути и `import type`, но не описывает формат блока импортов. Для `demo-app` принято не
разделять импорты пустыми строками на группы.

Нужно закрепить формат и порядок импортов в основном styleguide.

## GAP-002: Небольшие статические фрагменты JSX

**Состояние:** открыт.

Документация не объясняет, когда небольшой неизменяемый набор элементов следует записать прямо в JSX, а когда вынести в
массив и отобразить через `map`. В `demo-app` одноразовое содержимое карточек записано прямо в разметке, чтобы не создавать
искусственную модель данных.

Нужно описать критерий выбора без запрета на `map` для настоящих наборов данных.

## GAP-003: Размещение переключателя цветовой схемы

**Состояние:** открыт.

`infra/theme` публикует технический контракт цветовой схемы, а визуальные элементы не должны принадлежать `infra`.
Верхнеуровневый слой `ui` при этом не может зависеть от `infra` по матрице слоёв. Переключатель нужен в постоянной верхней
панели, поэтому он размещён как вложенный композиционный юнит
`compositions/layouts/main/ui/header/ui/theme-color-scheme-toggle` и использует фасет `infra/theme`.

Нужно добавить в документацию темы пример границы между техническим хуком, локальным элементом управления и возможным
универсальным компонентом верхнеуровневого слоя `ui`.

## GAP-004: Состояние ожидания динамического маршрута в React Router 7

**Состояние:** открыт.

Пример маршрутизатора использует динамические `lazy`-маршруты без `HydrateFallback` или `hydrateFallbackElement`. В
React Router 7 это приводит к предупреждению при начальной загрузке. В `demo-app` корневой маршрут явно задаёт
`hydrateFallbackElement`.

Нужно обновить инструкцию маршрутизации и согласовать название компонента ожидания.

## GAP-005: Алиасы TypeScript в Vite 8

**Состояние:** открыт.

Документация предлагает ручной `resolve.alias` либо установленный плагин чтения `tsconfig`. Vite 8 умеет читать `paths`
через `resolve.tsconfigPaths`, поэтому `demo-app` не использует дополнительный плагин и второй список алиасов.

Нужно обновить инструкцию платформы с учётом поддерживаемой версии Vite.

## GAP-006: Автономная имитация API

**Состояние:** открыт.

Документация описывает REST-клиент, доменный адаптер и SWR, но не определяет способ запуска демонстрационного приложения
без внешнего сервера. В `demo-app` для этой границы выбран MSW. OpenAPI-схема хранится в
`openapi/backend-api.openapi.json`, `generated`-клиент создаётся воспроизводимой командой, а обработчики MSW реализуют те
же четыре операции авторизации и профиля.

Нужно описать размещение обработчиков, запуск worker, использование схемы в разработке и отличие этого решения от
production API.

## GAP-007: Структура React-компонента и фасет юнита

**Состояние:** открыт.

В skill показана структура самостоятельного компонента-юнита, но не закреплена единая файловая форма обычного
внутреннего компонента. Для `demo-app` за основу взят шаблон `apps/admin/.templates/component` из проекта `extimia.ru`:

```text
component-name/
├── component-name.tsx
├── styles/
│   └── component-name.module.css
└── types/
    └── component-name-props.type.ts
```

Фасет `index.ts` добавляется к этой структуре только тогда, когда папка действительно является юнитом с отдельной
ответственностью и публичным контрактом. Внутренний компонент без фасета импортируется относительным путём внутри
владельца. Тип свойств компонента размещается в `types/{name}-props.type.ts`, а сам компонент получает обязательный
верхнеуровневый JSDoc по правилам styleguide.

Нужно согласовать эту структуру с правилами колокации и закрепить отличие обычного компонента от компонента-юнита в
основной документации.

## GAP-008: Генерация повторяемой структуры

**Состояние:** открыт.

В `react-reference` и `demo-app` сейчас нет каталога `.templates`, настроенного шаблона компонента и принятой команды
генерации. Из-за этого композиционные и UI-юниты, а также внутренние компоненты могут создаваться вручную в разной форме.

В исследованном проекте `extimia.ru` структуру из `.templates` создаёт CLI `@gromlab/create`. Он не требует глобальной
установки и запускается из каталога, в котором находится нужная `.templates`:

```bash
npx @gromlab/create <шаблон> <имя> [путь]
```

CLI ищет `.templates` только в текущем рабочем каталоге. Необязательный `[путь]` задаёт каталог вывода относительно этой
же рабочей директории. Путь к самим шаблонам через параметры не передаётся. В проекте с pnpm тот же CLI запускается через
`pnpm dlx @gromlab/create`. Для ручной работы из редактора эти же шаблоны поддерживает расширение VS Code
`Template File Generator | gromlab`, которое устанавливается на машину разработчика, а не в проект.

Нужно выбрать область `.templates` для `react-reference`, определить отдельные шаблоны для внутреннего компонента и
юнитов разных ролей и описать команды использования. Шаблон юнита должен создавать фасет, а шаблон внутреннего компонента
не должен его создавать. Существующий шаблон `component` из `extimia.ru` нельзя переносить без изменения, поскольку он
всегда создаёт `index.ts`.

## GAP-009: Формат JSDoc для типов и их полей

**Состояние:** открыт.

TypeScript styleguide требует JSDoc для каждого `type`, `interface`, `enum` и каждого их поля или значения. При этом
многострочная форма явно обязательна только для функций и классов, а пример полей типа использует однострочный JSDoc.
Это допускает два разных оформления одной категории документации.

В `demo-app` для типов, внутренних псевдонимов и полей принята единая многострочная форма JSDoc. Нужно закрепить или
отклонить это решение в styleguide и синхронизировать с будущими шаблонами генерации.

## GAP-010: Обязательная структура JSDoc React-компонента

**Состояние:** открыт.

JSX styleguide требует верхнеуровневый JSDoc для каждого React-компонента, но разрешает выбирать его объём в зависимости
от сложности. Для проекта требуется более точная единая структура: строка назначения, пустая строка и раздел
`Используется для:` с одной, двумя или тремя строками применения.

```tsx
/**
 * Отображает назначение компонента.
 *
 * Используется для:
 *  - первого сценария применения
 *  - второго сценария применения
 */
```

Нужно закрепить этот формат в JSX styleguide и добавить его во все шаблоны, создающие React-компоненты.

## GAP-011: Маршрутные адаптеры и экраны

**Состояние:** открыт.

Текущий архитектурный профиль использует группу `compositions/pages` для непосредственно подключаемых проекций React
Router. Название `pages` создаёт лишнюю аналогию с файловой маршрутизацией Next.js, хотя browser-only SPA имеет одну точку
запуска, а дерево URL объявляется в `app/router`. Самостоятельный route-файл не становится точкой разделения сборки без
динамического `import()`.

В `demo-app` принято следующее разделение ответственности:

- `app/router` владеет URL, вложенностью, перенаправлениями, общей обработкой ошибок и динамическим подключением фасетов;
- `compositions/routes` содержит адаптеры, непосредственно подключаемые к React Router через фасет `lazy.ts`;
- маршрутный адаптер может проверять доступ и параметры URL, выполнять перенаправление, подключать `Outlet` и определять
  область жизни публичного `Provider`;
- реализация подключаемого `Provider` остаётся у владельца в `domains` или `infra`;
- `compositions/screens` содержит завершённые экранные сценарии и владеет их разметкой и действиями;
- обычный маршрутный адаптер связывает экран с деревом URL и предоставляет форму компонента, которую ожидает React Router;
- маршрутный адаптер без отображаемого экрана допустим для проверки доступа, перенаправления, `Outlet` или области жизни
  публичного `Provider`.

В `demo-app` правило подтверждают следующие рабочие связи:

- `MainLayout` владеет постоянными верхней и нижней панелями и выводит маршрутную ветку через `Outlet`;
- `AuthenticatedRoute` ожидает сессию, перенаправляет гостя и выводит защищённую ветку через `Outlet`;
- `HomeRoute`, `SignInRoute`, `AccountRoute` и `NotFoundRoute` подключают соответствующие юниты `screens`;
- `HomeScreen`, `SignInScreen`, `AccountScreen` и `NotFoundScreen` владеют экранными сценариями;
- обычные переходы выполняются через `Link` либо внутри владельца полного пользовательского действия.

Нужно заменить группу `pages` на связку `routes` и `screens` в архитектурном профиле и документации маршрутизации,
описать фасеты и ответственность обеих групп и использовать `demo-app/src/compositions/routes/authenticated` как
проверяемый пример маршрутного адаптера без экрана.

## GAP-012: Проверка `generated`-кода на неиспользуемые параметры

**Состояние:** открыт.

`@gromlab/rest-api-codegen@5.2.4` создаёт в `ApiRequestClient.request<T, E>` параметр типа `E`, который не используется в
сигнатуре. TypeScript 5.9 сообщает `TS6133` при включённом `noUnusedParameters`, хотя файл полностью принадлежит
генератору и не должен редактироваться вручную. В `demo-app` сохранены `strict` и `noUnusedLocals`, но
`noUnusedParameters` временно отключён для `tsconfig.app.json`.

Нужно использовать `E` в контракте `generated`-клиента либо предоставить способ исключить `generated`-код из этой проверки,
после чего вернуть `noUnusedParameters` в `demo-app`.
