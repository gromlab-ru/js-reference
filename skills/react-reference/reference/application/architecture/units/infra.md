# Инфраструктурные юниты

Инфраструктурный юнит предоставляет одну техническую возможность без предметного смысла. Он скрывает интеграцию с
браузером, внешней системой или библиотекой за стабильным техническим контрактом.

## Назначение

Потребитель инфраструктурного юнита получает готовую техническую операцию или ресурс и не знает, как он настроен и
реализован.
Примеры таких возможностей:

- клиент конкретного внешнего API;
- браузерное хранилище;
- WebSocket-соединение;
- отправка телеметрии;
- Query Client;
- техническое подключение общей темы библиотеки компонентов;
- созданный генератором API SVG-спрайта;
- ограниченный базовый store общих клиентских статусов времени жизни приложения.

Название библиотеки или наличие технического файла само по себе не обосновывает юнит. Отдельная граница нужна, когда
у возможности есть реальный потребитель, собственный контракт, зависимости или жизненный цикл.

## Чем владеет инфраструктурный юнит

Инфраструктурный юнит владеет:

- техническим публичным контрактом;
- настройкой интеграции;
- преобразованием внешнего технического API в принятый проектом технический API;
- техническими результатами и ошибками;
- состоянием ресурса и числом его экземпляров;
- созданием, подключением, повторным подключением и очисткой ресурса;
- созданным генератором кодом и адаптацией внешней библиотеки, если они являются частью этой возможности.

Если возможность подключается к дереву React, Provider остаётся реализацией инфраструктурного юнита. Наличие JSX не
меняет роль:
потребитель по-прежнему получает техническую возможность, а не визуальный или предметный результат.

## Граница

Инфраструктурный юнит не должен:

- использовать предметные модели и термины;
- преобразовывать техническую ошибку в ожидаемый продуктовый исход;
- владеть пользовательским сценарием;
- реализовывать страницу, экран или продуктовый виджет;
- раскрывать внутреннюю конфигурацию без подтверждённого потребителя;
- создавать второй экземпляр общего ресурса рядом с каждым потребителем.

Доменный адаптер использует готовый технический контракт и преобразует его результат в предметный смысл. Композиция
может использовать инфраструктурный юнит напрямую для проекционной технической задачи, но не переносит к себе
настройку ресурса.

По проектному профилю `infra/theme` владеет только техническим подключением библиотеки компонентов, конфигурацией её
Provider и техническим контрактом цветовой схемы. Универсальные визуальные компоненты и визуальные правила остаются в
`ui`.

### Базовый store приложения

`infra/app-store` предоставляет технический механизм координации нескольких независимых верхнеуровневых потребителей и
обычного TypeScript-кода. Он хранит только клиентские статусы, которые живут всё время работы приложения, переживают
размонтирование отдельных потребителей и не принадлежат одному предметному, проекционному или визуальному владельцу.

Не превращай `app-store` в общий склад состояния. Ответы API и состояние запросов остаются в SWR, локальное состояние —
у ближайшего React-владельца, а состояние одного домена — в `domains/<name>/stores`. Новый статус нельзя добавлять только
потому, что его удобно импортировать из разных мест.

Создавай базовый store через `zustand/vanilla`, чтобы инфраструктурный код мог вызвать действие через
`appStore.getState()`. Для React публикуй отдельный хук и точные селекторы. Эталон находится в
[`demo-app/src/infra/app-store/`](../../../../demo-app/src/infra/app-store/), включая
[`app.store.ts`](../../../../demo-app/src/infra/app-store/app.store.ts),
[`use-app-store.hook.ts`](../../../../demo-app/src/infra/app-store/hooks/use-app-store.hook.ts) и
[`authentication-status.selector.ts`](../../../../demo-app/src/infra/app-store/selectors/authentication-status.selector.ts).

При защищённом `401` REST-клиент может удалить токен и сообщить общий статус `unauthenticated` через этот store. На
статус подписываются доменный `AuthGuard` и владелец жизненного цикла авторизации. Инфраструктурный REST-клиент не
импортирует SWR, не знает ключи текущей сессии и не очищает приватный кеш.

## Публичный контракт

Публикуй минимальные технические операции, типы и компоненты подключения, которые действительно нужны другим юнитам.
Фасеты `index.ts` и `lazy.ts` применяются по
[`архитектурному профилю`](../project-profile.md#публичные-фасеты).

Не публикуй внутренние параметры библиотеки только ради удобства глубокого импорта. Если потребителю приходится
повторять URL, заголовки, настройки соединения, правила очистки или конфигурацию Provider, публичный контракт не
закрывает ответственность юнита.

## Проверка

- Юнит предоставляет одну техническую возможность без предметного смысла.
- Потребитель не повторяет настройку и жизненный цикл ресурса.
- Публичный контракт не содержит предметных моделей и ожидаемых доменных ошибок.
- Provider или React hook не изменили техническую роль владельца.
- Базовый store содержит только подтверждённые общие статусы времени жизни приложения, а предметное состояние остаётся
  у домена.
- Доступ вне React проходит через vanilla store, а React-подписка выбирает точное значение селектором.
- Внутренняя конфигурация не раскрыта без реального потребителя.
- Подробности библиотеки находятся в её профильном документе, а не в архитектурном определении.
- Межюнитные импорты проходят через фасет и не создают цикл.
