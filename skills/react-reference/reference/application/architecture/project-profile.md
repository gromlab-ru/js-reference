# Архитектурный профиль React SPA

Этот документ закрепляет проектные решения, которые Unit Architecture оставляет команде приложения. Прочитай его до
проектирования или изменения архитектурной границы. Общие определения владельца, юнита, слоя, группы, сегмента и
зависимости остаются в skill `unit-architecture`.

Профиль действует в пределах корня клиентского React SPA. Он определяет используемые роли, маркеры публичных фасетов,
внутреннюю форму юнита и классификацию продуктовых проекций в слое `compositions`.

## Роли юнитов

Проект использует пять ролей:

| Слой | Результат юнита | Правила работы |
| --- | --- | --- |
| `compositions` | Продуктовая блочная UI-проекция | [`units/compositions.md`](units/compositions.md) |
| `domains` | Предметная возможность | [`units/domains/README.md`](units/domains/README.md) |
| `infra` | Техническая возможность | [`units/infra.md`](units/infra.md) |
| `ui` | Универсальная визуальная возможность | [`units/ui.md`](units/ui.md) |
| `shared` | Чистый детерминированный фундамент | [`units/shared.md`](units/shared.md) |

Порядок выбора роли и общая граница React-компонента описаны в [`обзоре юнитов`](units/README.md). `app` является
интеграционной границей запуска и не создаёт отдельную роль юнита в этом проекте.

Техническое подключение общей темы библиотеки компонентов принадлежит `infra/theme`. Универсальные визуальные
компоненты и визуальные правила проекта остаются в `ui`. Это проектное уточнение границы интеграции и визуальной
ответственности.

## Публичные фасеты

В проекте используются два маркера фасета:

| Фасет | Назначение |
| --- | --- |
| `index.ts` | Обычный публичный API для статических импортов |
| `lazy.ts` | Минимальная точка входа для динамического импорта |

Наличие `index.ts` или `lazy.ts` объявляет содержащую их папку юнитом. Объявленный юнит обязан иметь отдельную
ответственность, непустой публичный контракт и допустимые зависимости. Оба фасета представляют один логический API
юнита и не содержат реализацию.

`index.ts` экспортирует только возможности, нужные обычным межюнитным потребителям. Импорт выполняется через путь
юнита:

```ts
import { AccountScreen } from '@/compositions/screens/account'
```

`lazy.ts` создаётся только при подтверждённом разделении кода. Он экспортирует минимальный контракт загрузчика и
импортируется только через `import()`:

```ts
const loadAccountPage = () => import('@/compositions/pages/account/lazy')
```

Для динамического маршрута React Router фасет публикует компонент страницы под ожидаемым библиотекой именем:

```ts
export { AccountPage as Component } from './account-page'
```

При необходимости этот же фасет может экспортировать `ErrorBoundary`. Предметные `loader` и `action` в нём не
размещаются: серверные данные и изменения принадлежат доменным API.

Юнит может иметь один или оба фасета. Если API используется только динамическим потребителем, одного `lazy.ts`
достаточно. Не создавай второй фасет без отдельного способа потребления.

Имена `index.ts` и `lazy.ts` зарезервированы во всём корне приложения. Не используй их для внутренних повторных
экспортов. Внутренняя папка с таким файлом становится вложенным юнитом и проходит все проверки архитектурной границы.
Любой межюнитный импорт, включая `import type` и динамический импорт, проходит через соответствующий фасет.

## Структура юнита

Юнит содержит фасеты, основные файлы реализации и только необходимые сегменты:

```text
unit-name/
├── index.ts          # если нужен обычный публичный API
├── lazy.ts           # если нужна динамическая загрузка
├── unit-name.tsx     # если ответственность реализуется React-компонентом
├── config/
├── helpers/
├── hooks/
├── providers/
├── stores/
├── styles/
├── types/
└── ui/
```

Это перечень допустимых частей, а не обязательный шаблон. Не создавай пустые файлы и папки ради одинакового дерева.
Небольшая реализация может оставаться в корне юнита. Когда файлы образуют одну из закреплённых ниже категорий, используй
соответствующий сегмент.

### Общие сегменты

| Сегмент | Что находится внутри |
| --- | --- |
| `config/` | Декларативная конфигурация владельца |
| `helpers/` | Небольшие внутренние операции и вычисления владельца |
| `hooks/` | React-хуки состояния и жизненного цикла владельца |
| `providers/` | Контексты и компоненты Provider владельца |
| `stores/` | Клиентское состояние владельца |
| `styles/` | CSS Modules, оформляющие DOM владельца |
| `types/` | Внутренние и публикуемые типы владельца |
| `ui/` | Внутренние React-компоненты и вложенные компоненты-юниты владельца |

Одинаково названный сегмент имеет этот смысл во всех слоях. Папка сегмента не имеет фасета, не является владельцем и
не импортируется как самостоятельный API. Папка внутри `ui/` становится вложенным юнитом только при появлении
`index.ts` или `lazy.ts`; без маркера она остаётся внутренней реализацией ближайшего владельца.

### Профильные сегменты

Профильные сегменты уточняют устройство отдельных слоёв и применяются только там, где нужна соответствующая роль:

| Сегмент | Применение | Что находится внутри |
| --- | --- | --- |
| `adapters/` | `domains` | Преобразование технического API в предметную операцию |
| `mappers/` | `domains` | Преобразование DTO и других внешних значений в предметные типы и обратно |
| `errors/` | `domains` | Ожидаемые предметные ошибки и их проверки |
| `source-errors/` | `domains` | Проверки технических ошибок конкретного источника |
| `operations/` | `infra` | Отдельные технические операции владельца |
| `generated/` | `infra` | Код, полностью принадлежащий генератору |

Профильный документ слоя или библиотеки объясняет порядок применения такого сегмента, но не переопределяет его смысл.
Новый сегмент добавляется в этот профиль только после появления устойчивой категории файлов, которой не подходит
существующее определение.

## Структура compositions

Слой `compositions` использует четыре группы продуктовых UI-проекций:

```text
compositions/
├── layouts/
├── pages/
├── screens/
└── widgets/
```

Группа содержит юниты и не имеет собственного фасета или реализации. Она только классифицирует проекционные
ответственности и помогает находить их в слое. Группа не задаёт уровень, приоритет или отдельное направление
зависимостей. Пустая группа не создаётся.

### layouts

`layouts/` содержит устойчивые каркасы приложения или веток маршрутов. Юнит этой группы определяет размещение общих
областей, например навигации, основного содержимого и нижней части страницы, но не владеет предметными правилами
отображаемых сценариев.

Такой юнит может собирать готовые публичные возможности и принимать изменяемое содержимое через свойства или механизм
вложенных маршрутов.

### pages

`pages/` содержит проекции, которые непосредственно подключаются к маршрутам. Юнит этой группы собирает готовые
публичные возможности для отображения конкретного URL, но не владеет самим деревом URL.

Страница может читать параметры и состояние маршрута через React Router. Для динамического подключения она публикует
`lazy.ts` с экспортом `Component`. Обычный `index.ts` добавляется только при наличии статического потребителя.

### screens

`screens/` содержит завершённые экранные проекции, не зависящие от конкретного URL. Юнит этой группы представляет
связный пользовательский сценарий и собирает необходимые ему публичные возможности.

Если проекция читает параметры или состояние маршрута либо существует только для одного URL, исходным владельцем
является юнит группы `pages`, а не `screens`.

### widgets

`widgets/` содержит крупные самостоятельные области интерфейса. Юнит этой группы может собирать необходимые ему
публичные возможности, но не представляет целую страницу и не знает о дереве маршрутов.

Не поднимай локальную часть страницы, экрана или каркаса в `widgets` ради предполагаемого переиспользования.

Новая группа появляется только для устойчивой роли нескольких юнитов, которую нельзя однозначно отнести к четырём
существующим группам. До создания группы опиши её ответственность, потребителей и отличие от существующих групп в этом
профиле.

## Граница app и compositions

`app` связывает готовые публичные API со средой выполнения React. В маршрутизации он владеет конфигурацией React Router,
деревом URL, перенаправлениями, глобальными обработчиками ошибок маршрутов и динамическим подключением фасетов.

Отображаемая проекция маршрута принадлежит `compositions/pages`. Конфигурация маршрута импортирует её `lazy.ts`, но не
реализует страницу внутри `app`:

```text
app/router → compositions/pages/*/lazy.ts
```

Тонкий служебный файл внутри `app` допустим, если React Router требует отдельную форму, которую нельзя предоставить
напрямую через фасет страницы. Такой файл только адаптирует публичный контракт и не присваивает себе отображение или
предметное поведение.

## Проверка

- Каждый объявленный юнит относится к одной из пяти проектных ролей.
- Каждый `index.ts` и `lazy.ts` принадлежит юниту с отдельной ответственностью и непустым контрактом.
- Статические потребители используют `index.ts`, а динамические — `lazy.ts` через `import()`.
- Внутренние папки не используют зарезервированные маркеры для повторных экспортов.
- Сегменты соответствуют словарю, не имеют фасетов и создаются только при наличии кода.
- Вложенный юнит не импортирует родителя, предков или соседних детей.
- Каждый юнит `compositions` однозначно отнесён к принятой группе.
- `app` владеет конфигурацией маршрута, а `compositions/pages` — отображаемой страницей.
- Служебные файлы `app` не получили искусственный фасет.
- Зависимости соответствуют матрице Unit Architecture и не образуют циклов.
