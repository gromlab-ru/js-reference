# JSDoc для объявлений `type`

Опиши значение глазами того, кто будет с ним работать. Например, `A & B` уже показывает состав типа.
В JSDoc нужно объяснить, зачем нужны данные, которые удовлетворяют обоим типам одновременно.

## Шаблон

```text
/**
 * <Что представляет значение этого типа и для какой задачи оно нужно.>
 *
 * <Общее условие, если без него значение можно понять неверно.>
 */
type <Имя> = <выражение типа>
```

## Правила

1. Ставь многострочный JSDoc перед `type`. Первой фразой назови назначение, даже если справа стоит простой тип.
   У суммы уточни единицы: например, рубли или копейки. У идентификатора укажи, какую запись по нему находят.
2. **Пересечение `A & B`.** Назови задачу, для которой обе части нужны вместе. Второй абзац добавь, только если
   у сочетания есть своё условие: например, что подтверждает запись целиком.
   Фразы «соединяет `A` и `B`» недостаточно: из неё непонятно, где использовать новый тип.
3. **Объектные поля.** Описывай каждое поле там, где оно объявлено, [по правилам объекта](object-interface-enum.md#правила).
   Для объектной части объединения или пересечения используй имя типа или интерфейса по правилам `ts-standarts`.
   В комментарии над `A & B` или `A | B` эти описания не повторяй.
4. **Объединение `A | B`.** Если `type` целиком перечисляет строковые или числовые литералы через `|`, опиши **каждое
   значение ровно один раз, в порядке объявления**. После назначения оставь пустую строку и составь список
   «значение — смысл» в том же JSDoc над `type`. Начинай пункт с `* - ` и бери значение в обратные кавычки.
   У строк обычно достаточно текста без кавычек TypeScript; сохрани их для пустой строки или чтобы отличить `'1'`
   от числа `1`. Для остальных объединений, например `Date | null` или двух именованных типов, поясняй только
   неочевидные различия.
5. **Тип функции.** Назови роль вызова. Для передаваемой функции важно, кто и когда её вызовет. Оформи аргументы
   и неочевидные результаты [по правилам функций](function.md#правила).
6. У кортежа поясни смысл позиций, если перестановка меняет смысл значения, но допустима по типам. У типа с
   параметром `T` объясни, какие данные он связывает, если это важно для использования.

## Пример: события доставки

Для события объясни, какой факт оно подтверждает. В этом примере перевозчик сообщает о физическом приёме посылки.

```ts
/**
 * Событие в истории доставки посылки.
 *
 * - `shipment.created` — отправление зарегистрировано; передача перевозчику
 *   этим событием не подтверждается
 * - `shipment.accepted_by_carrier` — перевозчик принял саму посылку
 * - `shipment.arrived_at_sorting_center` — посылка поступила в сортировочный
 *   центр; это событие отмечает прибытие, а не завершение сортировки
 * - `shipment.received_by_recipient` — подтверждено вручение получателю
 */
type DeliveryEvent =
  | 'shipment.created'
  | 'shipment.accepted_by_carrier'
  | 'shipment.arrived_at_sorting_center'
  | 'shipment.received_by_recipient'
```

## Пример: назначение на рейс и подтверждение погрузки

```ts
/**
 * Данные для поиска посылки по этикетке при погрузке.
 */
type ParcelRef = {
  /** Идентификатор посылки на этикетке. */
  parcelId: string
}

/**
 * Данные для поиска рейса в расписании перевозчика.
 */
type FlightRef = {
  /** Идентификатор рейса в расписании. */
  flightId: string
}

/**
 * Назначение посылки на рейс в погрузочной ведомости.
 *
 * Запись в ведомости ещё не подтверждает погрузку.
 */
export type PlannedLoad = ParcelRef & FlightRef

/**
 * Отметка о том, когда подтвердили погрузку.
 */
type LoadConfirmation = {
  /** Время подтверждения погрузки по часам сервера. */
  loadedAt: Date
}

/**
 * Подтверждение погрузки посылки на назначенный рейс.
 */
export type ConfirmedLoad = PlannedLoad & LoadConfirmation
```

## Проверка

- У `DeliveryEvent` четыре значения — найди четыре пояснения в том же порядке. Чтобы подтвердить смысл
  `shipment.accepted_by_carrier`, проверь, в какой момент создаётся событие, или сверься с описанием протокола.
  Если неизвестно, принял перевозчик заявку или саму посылку, уточни у автора.
- Достаточно ли `PlannedLoad`, чтобы сообщить клиенту, что посылка уже на борту? Нет: верхний комментарий
  отличает назначение от подтверждения. Это полезнее, чем перечень `parcelId` и `flightId`.
- Чтобы узнать, по чьим часам записано `loadedAt`, прочитай JSDoc этого поля у `LoadConfirmation`.
  Чтобы узнать, откуда берётся `parcelId`, прочитай подпись у `ParcelRef`.
