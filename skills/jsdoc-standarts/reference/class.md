# JSDoc для классов

Над классом объясни, для чего нужен экземпляр. У конструктора читатель должен узнать, как получить экземпляр
в нужном состоянии, у поля — что означает его значение, у метода — чего ожидать от вызова.

## Шаблон

```text
/**
 * <Что представляет один экземпляр и для какой задачи он нужен.>
 *
 * <Общее условие работы с экземпляром, если без него легко ошибиться.>
 */
class <Имя> {
  /** <Что означает поле при чтении.> */
  <поле>

  /**
   * <В каком состоянии будет экземпляр сразу после создания.>
   *
   * `<аргумент>`: <что передать при создании>.
   */
  constructor(<аргумент>) { … }
}
```

## Правила

1. **Класс.** Поставь многострочный JSDoc над объявлением. Если есть гарантия, важная при работе с экземпляром
   в целом, опиши её вторым абзацем. Список полей и методов уже виден в классе.
2. **Конструктор.** Поставь один многострочный JSDoc над `constructor`, как над функцией. Начни с того, что будет
   верно сразу после `new`: например, повлияют ли изменения исходного списка на созданный экземпляр.
   Все аргументы и особые случаи опиши в этом же блоке [по правилам функций](function.md#правила). Если конструктор
   отклоняет значение, укажи, какая ошибка возникнет. Сигнатуру, которая с учётом отступа помещается в 120 колонок,
   оставляй в одну строку. Более длинную разбивай по одному параметру на строку. Если явного конструктора нет,
   важное начальное состояние опиши над классом.
3. **Поля.** Описывай значение там, где объявлено поле, [так же, как у объекта](object-interface-enum.md#правила).
   Для простого поля достаточно одной строки. Особые значения и диапазоны перечисли в JSDoc самого поля.
   Поле `static readonly`, которое задаёт общий для класса лимит или код, опиши как [константу](constant.md).
   Параметру, который одновременно объявляет поле (например, `readonly flightId`), обычно достаточно описания
   над конструктором. Если при чтении поля нужно отдельное пояснение, объяви поле в теле класса и поставь JSDoc там.
4. **Методы.** И для метода экземпляра, и для статического метода используй [правила функций](function.md).
   Если вызов меняет состояние экземпляра, поясни, что изменится для вызывающего кода.

## Пример: план погрузки

```ts
/**
 * План рейса для проверки посылок перед погрузкой.
 */
export class LoadingPlan {
  /**
   * Идентификатор посылки, с которой начинается погрузка.
   *
   * - `null` — в плане нет посылок
   */
  readonly firstParcelId: string | null

  /** Идентификаторы посылок, назначенных на рейс. */
  readonly #parcelIds: ReadonlySet<string>

  /**
   * Фиксирует состав рейса: последующие изменения переданного списка
   * не меняют план погрузки.
   *
   * `flightId`: идентификатор рейса из расписания перевозчика.
   *
   * `parcelIds`: идентификаторы посылок в порядке погрузки.
   *   - повтор идентификатора — конструктор выбросит ошибку
   */
  constructor(readonly flightId: string, parcelIds: readonly string[]) {
    const uniqueIds = new Set(parcelIds)
    if (uniqueIds.size !== parcelIds.length) {
      throw new Error('Посылка указана в плане дважды')
    }

    this.#parcelIds = uniqueIds
    this.firstParcelId = parcelIds[0] ?? null
  }

  /**
   * Проверяет, назначена ли посылка на этот рейс.
   *
   * `parcelId`: идентификатор посылки с этикетки.
   */
  hasParcel(parcelId: string): boolean {
    return this.#parcelIds.has(parcelId)
  }
}
```

## Проверка

- Создали план по списку `['B', 'A']`, затем добавили `'C'` в исходный список. Какую посылку грузят первой
  и что вернёт `hasParcel('C')`? По комментариям можно ответить до чтения кода: `'B'` и `false`.
- Можно ли вызвать `new LoadingPlan('R1', ['A', 'A'])` и получить план? Ответ ищи у `parcelIds` в JSDoc конструктора:
  повтор идентификатора приведёт к ошибке.
- Наведи курсор на `plan.firstParcelId`. Должно быть понятно, что `null` означает пустой план, без перехода
  к конструктору.
