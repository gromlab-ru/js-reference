# JavaScript

Применяй этот документ к `.js` и JavaScript-частям `.jsx`. Он определяет конструкции, idioms, именование значений,
runtime-проверки и JSDoc JavaScript-кода. Проектные правила форматирования, файлов и module boundaries определяет
[`code-style.md`](../code-style.md).

## Объявления и функции

- Используй `const` по умолчанию.
- Используй `let` только когда переменная действительно переназначается.
- Не используй `var`.
- Не изменяй входной объект или массив, если mutation не является явной частью контракта.
- Декомпозируй функцию, когда она одновременно решает несколько независимых задач.
- Не скрывай важный side effect за именем, похожим на чистое вычисление.

```js
/**
 * Возвращает отображаемое имя пользователя.
 */
const getDisplayName = (user) => user.displayName
```

## Ранние возвраты и ветвление

- Используй ранние возвраты для отсутствующих данных, ошибок, запрещённых состояний и других guard conditions.
- Сначала обрабатывай исключающие условия, затем размещай основной сценарий функции.
- Не добавляй `else` после ветки с безусловным `return` или `throw`.
- Не оборачивай основной сценарий в несколько уровней `if`, если вложенность можно заменить guard clauses.
- Не добавляй ранние возвраты механически, если линейное условие читается проще.

Хорошо:

```js
/**
 * Возвращает имя доступного активного пользователя.
 */
const getUserName = (user) => {
  if (!user) {
    return 'Гость'
  }

  if (!user.isActive) {
    return 'Неактивный пользователь'
  }

  return user.name
}
```

Плохо:

```js
/**
 * Возвращает имя доступного активного пользователя.
 */
const getUserName = (user) => {
  if (user) {
    if (user.isActive) {
      return user.name
    } else {
      return 'Неактивный пользователь'
    }
  } else {
    return 'Гость'
  }
}
```

## Именование значений

- Переменные и функции называй в `camelCase`.
- Классы называй в `PascalCase`.
- Custom hooks называй в форме `useSomething`.
- Массивы называй во множественном числе.
- Списки идентификаторов называй `*Ids`.
- Словари и maps называй `*ById`, `*Map` или `*Dict`.
- Boolean-значения начинай с `is`, `has`, `can` или `should`.
- Внутренние обработчики называй `handle*`.
- Callback-параметры и свойства называй `on*`.
- Функция должна называться по выполняемому действию или возвращаемому значению.
- Избегай общих имён `data`, `item`, `value`, `result`, если роль можно выразить точнее.

```js
const userIds = ['u1', 'u2']
const usersById = {}
const isReady = true

/**
 * Обрабатывает отправку формы.
 *
 * Запускает сохранение подготовленных данных.
 */
const handleSubmit = () => {
  // ...
}
```

## Константы и стабильные значения

- Обычную локальную переменную, объявленную через `const`, называй в `camelCase`.
- Переиспользуемую константу верхнего уровня называй в `SCREAMING_SNAKE_CASE`.
- Связанный набор стабильных runtime-значений группируй в константный объект.
- Ключи enum-like объекта называй в `SCREAMING_SNAKE_CASE`.
- Значения сохраняют формат runtime-контракта и не обязаны быть в uppercase.
- Не переименовывай непрозрачные значения внешнего API ради code style.
- Если нужны внутренние значения, сопоставляй внешний контракт с ними на границе владельца.
- Если объект должен быть неизменяемым в runtime, явно используй `Object.freeze`.

```js
export const MAX_PAGE_SIZE = 100

export const PAYMENT_STATUS = Object.freeze({
  PENDING: 'pending',
  PAID: 'paid',
  FAILED: 'failed'
})

const currentPage = 1
```

## Данные и runtime-проверки

- Проверяй внешние данные до использования, даже если источник считается стабильным.
- Не смешивай отсутствие значения с falsy-значениями: `0`, `false` и `''` могут быть валидными.
- Не используй truthy-проверку, если контракт требует различать `null`, `undefined` и другие falsy-значения.
- Повторяющуюся проверку формы данных выноси в именованный predicate.
- Не считай объект валидным только потому, что чтение одного поля не завершилось ошибкой.
- Преобразуй внешний формат во внутреннюю модель на границе владельца, если их контракты различаются.

```js
/**
 * Проверяет наличие строкового идентификатора пользователя.
 *
 * @param {unknown} value Проверяемое runtime-значение.
 * @returns {boolean} Результат проверки.
 */
const isUser = (value) => {
  return typeof value === 'object' && value !== null && typeof value.id === 'string'
}
```

## JSDoc

Каждая именованная JavaScript-функция и каждый класс имеют многострочный JSDoc непосредственно перед объявлением.
Правило распространяется на function declarations, именованные function expressions, arrow functions в именованной
переменной, handlers и custom hooks.

- Описывай назначение сущности, а не синтаксис реализации.
- Добавляй важную механику, ограничения и результат только когда они неочевидны из имени.
- Описывай через `@param` и `@returns` значимые контракты, которые не выражены другими средствами проекта.
- Не документируй обычные локальные переменные и очевидные inline callbacks.
- Не используй фиксированный шаблон и не раздувай простое описание обязательными секциями.

Для простой функции достаточно краткого описания:

```js
/**
 * Возвращает отображаемое имя пользователя.
 */
const getDisplayName = (user) => user.name
```

Для сложной функции добавляй необходимый контекст:

```js
/**
 * Собирает дерево категорий из плоского списка.
 *
 * Категории без родителя попадают в корень дерева.
 *
 * @param {Category[]} categories Плоский список категорий.
 * @returns {CategoryNode[]} Дерево категорий.
 */
export const buildCategoryTree = (categories) => {
  // ...
}
```

## Проверка

- Functions, values, collections, booleans и handlers названы по роли.
- Для неизменяемых bindings используется `const`, а `let` применяется только при переназначении.
- Guard conditions обработаны до основного сценария без лишней вложенности и `else`.
- Константы верхнего уровня и enum-like наборы названы по своей роли.
- Внешние данные проверяются до использования, falsy-значения не смешиваются с отсутствием.
- Именованные функции и классы имеют достаточный JSDoc.
